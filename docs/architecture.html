controlroom: architecture and build plan

This document is the build spec: a supervisor agent should be able to build controlroom from it alone. A prototype at ../controlroom-old validated many of these ideas; proven parts of it are ported selectively (see "Port map from the prototype"). Status: draft for review.

Model (remote tools, accepted): pi runs only on the controlroom server, in the agent daemon (controlroom-agentd); execution hosts run only controlroomd in the host role (workspaces, named PTY shells, a tool executor with a journal, jobs, files) plus nono. A session has one or more workspaces (machine:path), the agent addresses files as machine:path, and projects are groups of tasks. The wire contract is docs/protocol.md (source of truth: crates/protocol); rationale, spike evidence and the phased plan are in docs/design/remote-tools.md.

0. Summary

controlroom is a self-hosted web app for supervising pi coding-agent sessions that run on many Linux machines, reached over SSH. Its architecture:

  • One deployment model: a persistent web server (PWA, OIDC). The desktop app is gone.
  • pi on the server, tools on the hosts: the agent daemon on the server runs every pi session; hosts only execute tools in the session's workspaces, reached through the controller over SSH. A link blip pauses a tool call; it never reruns or loses one.
  • Agent-neutral core: a driver (native pi RPC) folds raw stdio into one timeline model. The protocol and UI never see agent-specific payloads.
  • The agent daemon as the agent runtime: jobs, subagents as child sessions, a mailbox, injection, a shared todo list with auto-continue, and non-blocking questions. Agents reach these through the controlroom pi extension.
  • Sandboxed by default with nono, twice: pi on the server sees only the model hosts and its agent socket (no project files); on each host, shells, jobs and file tools are confined to the workspace, with credentials injected outside the sandbox, an egress allowlist, and approvals routed to controlroom.
  • Protocol 1.0: agent-neutral and tolerant of additions.
What carries over: the hard, proven parts. Those are the detached supervisor, the transcript as the source of truth, exactly-once recovery algorithms, SSH, key handling and bootstrap, OIDC and request hardening, Web Push, the UI shell, Nix packaging, and the test scenarios. Each is ported deliberately (reviewed, adapted, known bugs fixed). Nothing is copied wholesale.

1. Product goals

  • One place to discover, organize and interact with agent sessions across many machines. A failed machine never blocks the others.
  • Reliable attention signals:
    • needs an approval (blocking) or has an open question (non-blocking, a lighter tier);
    • failed or interrupted;
    • finished and unread.
    Connectivity is shown separately from agent state, and silence is never treated as failure.
  • Remote work continues independently of clients: the laptop sleeps, the browser closes, the web server or a host daemon restarts or upgrades, a host's link drops, and the agent keeps going (a tool call on an unreachable host waits; it never reruns).
  • Deliberate control: start, queue, send now, cancel and close are explicit. Disconnecting never cancels. Reconnecting never duplicates prompts or decisions.
  • Agents collaborate under user control: subagents, background jobs, shared todos, and messaging across machines within an explicit sandbox and contact policy.
  • User ownership: agents use the machine's own environment and the user's chosen harness. No hosted execution.

Invariants (carried over from the prototype; they must hold)

  1. Log before write: every line sent to an agent goes into the transcript (and is fsynced) before the agent sees it.
  2. The transcript is the truth: state and timeline are folds over the transcript. SQLite holds metadata, indexes and snapshots.
  3. Exactly once: every mutating command carries an op_id, deduplicated in the same transaction as its effect. A failed commit discards its outbound writes. Prompts are never resent automatically, and decisions are never reused.
  4. One reconcile loop per session decides what to write next. While the state is in doubt (just after a restart), no writes happen at all, answers included, until a supervisor barrier confirms that earlier writes have been logged.
  5. Disconnecting does nothing. No action is ever triggered by a client going away.
  6. Detached supervisors: agents survive client loss, web restarts and agent-daemon restarts or upgrades; shells and jobs survive host-daemon restarts and upgrades. Supervisors run from immutable versioned paths.
  7. Tool calls on hosts are keyed by the tool call id: reads are idempotent, writes are journaled, atomic and compare-and-swap, and bash is at-most-once (journaled before it runs; a resend attaches to the running command or returns its result, never reruns). A link loss pauses a call; it never duplicates or silently drops one.

5. Protocol (agent-neutral)

5.1 Principles

  • JSON-RPC 2.0 with newline-delimited framing. A per-method Method trait ties each method to its params and result types. ts-rs generates the TS, and a CI drift check runs under Nix.
  • Tolerant of additions:
    • every extensible enum (error kinds, events, annotations, timeline kinds, request kinds) has an Unknown fallback;
    • a response whose body doesn't parse fails its own request id, never the connection;
    • every call has a default timeout.
  • Versioning: major.minor, where a major mismatch means incompatible and minor versions only add. Optional features are negotiated through hello.capabilities (e.g. "jobs", "shells", "remote_tools").
  • Agent-neutral: no pi types on the wire. Raw frames go out only on an explicit debug subscription (raw: true).
  • Ids: ULID strings. RemotePath is a POSIX string newtype, never std::path. Timestamps are unix ms.

5.2 Session model

Sessions are global: the agent daemon owns them and their ids, and nothing session-scoped carries a machine. A session reaches files only through its workspaces.

5.3 Agent daemon API (controller ↔ controlroom-agentd)

  • hello (versions, capabilities, daemon id, controller id, role). A daemon serves exactly one controller at a time: a hello from a different controller is rejected while one is connected (a typed conflict error); a hello from the same controller replaces its old connection, so reconnects work. A local debugging client (ctl) connects with a debug role and is not the controller.
  • sessions.subscribe {since_rev}: summaries feed, with a snapshot fallback. A persisted rev log survives restarts.
  • session.subscribe {id, since_seq, raw?} (the UI asks for raw only on demand, when the raw view or a seq link is opened): timeline ops (upsert / append_text / end, each with a source seq range). Served from the materialized timeline, not by re-folding the whole transcript.
  • Commands (all carry an op_id):
    • session lifecycle: session.create {workspaces[{machine_id, path}], name?, parent_id?, sandbox?, prompt?} (every workspace's machine must be connected), session.workspace_add|remove, prompt, cancel, close, reopen, resume, start_fresh, delete;
    • session state: update (name, auto_send, auto_continue, budget), mark_read, mark_unread, set_option;
    • queue: queue.send_now|edit|remove|reorder|resume;
    • requests: request.respond {request_id, choice|answers, then?}, one method for permissions, questions, dialogs, host sandbox approvals and waits for terminal input;
    • todos: todo.add|update|remove|reorder;
    • jobs: job.list|logs|kill|follow|unfollow;
    • misc: agents.list, doctor.report, settings.get|set.
  • Host bridge, pull-style (the agent daemon never calls the controller): the controller calls hostops.subscribe and gets every pending host request, then hostops.request / hostops.withdraw notifications; it sends each request to its host when connected (again on the next connection if the response was lost: every host method is idempotent) and answers with hostops.respond {id, result|error}. It forwards every host notification with hostops.notify and reports its machines (names, availability, host epochs, grace) with hostops.machines.
  • The mailbox is local to the agent daemon: no outbox or inbox.
  • Errors: typed kinds (busy, already_resolved, deleted, not_resumable, unknown_session, invalid_state, invalid_params, unsupported, agent_unavailable, sandbox_unavailable, incompatible_version, machine_unavailable, conflict, lost, shell_gone, connection_lost, …) plus Unknown.

5.3b Host API (controller ↔ controlroomd host role)

  • hello (same single-controller rule) → host version, daemon id, epoch (new on every daemon start), capabilities (shells, pty, jobs, sandbox_approvals).
  • workspace.open {workspace_id, session_id, path, sandbox} → root, home, instruction files (AGENTS.override.md / AGENTS.md / CLAUDE.md from / down to the root) and skills; workspace.close.
  • shell.open {workspace_id, name, cwd?} (idempotent by name), shell.close, shell.list; notification shell.changed.
  • tool.run {call_id, workspace_id, op} with op one of read · read_bytes · stat · write (CAS by expect_sha256) · ls · find · grep · bash {shell, command, timeout_s} · job_run · job_follow · job_unfollow · job_kill · job_status; tool.attach, tool.cancel, journal.ack; notifications tool.output, tool.waiting_input.
  • jobs.subscribe {since} + jobs.event + jobs.ack {rev}: the persisted job event log (§8 Job).
  • approvals.subscribe + approval.request / approval.closed + approval.respond: sandbox approvals of the host's workspaces.
  • fs.list (the user's own access, for the new-session dialog and file browser) and doctor.report.

5.4 UI API (browser ↔ controller)

  • hello (server version, protocol, user, push capability).
  • state.subscribe (epoch+rev cursor): one aggregated feed of machines (incl. connectivity and doctor), sessions (global, each with its workspaces, their availability and its shells, plus its project membership: the projects of its linked tasks, else "Unassigned"), overlaps[] (directories used by several open sessions, for the warning), projects, tasks, grants, schedules, devices and contact requests.
  • Pass-through of every session/queue/todo/job/request command to the agent daemon, unchanged (no machine_id). fs.list names a machine; doctor.report a machine or the server.
  • session.subscribe: ref-counted, shared by tabs, resumed without duplicates.
  • machines.* (add → add_confirm, confirm_host_key, remove, reconnect, upgrade, set_settings incl. auto_upgrade and the tool-call grace), keys.* (incl. rotate), projects.* (name and color: projects are task groups), tasks.* (project_ids, session links, checklist), grants.*, notifications.* (web push only), schedules.*, sandbox.*, client.focus.
  • Connectivity per machine: connected · connecting · unreachable · incompatible · action_required{host_key_changed | auth_failed | host_key_unconfirmed | controller_conflict} · plus update_available.

5.5 Agent API (extension ↔ agent daemon)

A per-session unix socket and token (spec §9). Besides questions, todos, notices and jobs it carries the remote tools (capability remote_tools): session.info (workspaces with their instruction files and skills, shells; also pushed on change), host.call {call_id, machine, op} (one host operation of a tool; the agent daemon checks machine is one of the session's workspaces), host.cancel, shell.open|list|close, and the notifications host.output and host.waiting_input. Details: docs/protocol.md §8.

6. Daemons: supervisor, runtime, drivers, tool executor

The runtime, the drivers and the agent-kind supervisors run in the agent daemon on the server (agent.sqlite). The host daemon keeps the pty and job supervisors, the tool executor and its journal, the job event log (host.sqlite), the fs worker and doctor. Both stores use versioned migrations.

6.1 Supervisor (port from the prototype, extend)

  • Keep: flock single writer, log-then-fsync-then-write, partial-tail recovery, one writer role, exit drain, setsid re-exec, SIGHUP ignored, meta record, sync.
  • Add:
    • a spawn spec {kind: agent|job|pty, argv|shell, env-file, cwd, sandbox profile, stdin: pipe|null, timeout};
    • a barrier operation that confirms all earlier writes are logged;
    • fsync on a blocking thread, not the async worker;
    • a line-length cap;
    • a seq→offset index;
    • kill the process group on exit;
    • later: PTY byte records, raw writes and resize.
  • Launch: under nono (see "Sandboxing"), keeping $SHELL -lc for PATH. Login-shell noise on stdout is non-JSON and the drivers ignore it.
  • Kinds by place: agent on the server (pi); pty (shells, with byte records) and job on hosts, under the workspace's profile.

Send-now strategy belongs to the driver:

  • pi: native steering, sent as prompt with streamingBehavior:"steer": if the run settles before pi reads the line it starts the next run (a plain steer would wait in pi's queue for the next prompt). Its run is labelled steer;
  • a driver without steering (e.g. FakeDriver modes): cancel at a safe point.

Every written line embeds its op_id/queue_id so exactly-once can be derived from the transcript. The id floor is persisted.

6.3 PiDriver (new)

  • Launch: pi --mode rpc --no-builtin-tools --no-context-files --no-skills --session-id …, or --session <abs file> to resume, in an empty per-session scratch cwd (--session-dir under the agent daemon's session dir); the extension provides the tools, the workspace context and the skills. Strict LF JSONL (never Node-readline semantics), correlated by id.
  • Remote tools keep pi's names (read write edit bash grep find ls) and argument shapes, so the timeline mapping (titles, kinds, diffs) is unchanged.
  • Runs: from agent_start to agent_settled{aborted}.
  • Outcome: taken from the assistant stopReason (error → failed, length → max_tokens, aborted → cancelled) plus auto_retry_end. No end_turn heuristics.
  • Commands: prompt after the run settles or with streamingBehavior ("steer" for send-now and waking injections, "followUp"); steer (non-waking injections, which wait for the next run), abort, clear_queue; model and thinking setters; get_state, get_commands, get_session_stats; new_session{parentSession} for start fresh; extension_ui_response.
  • Events mapped to the timeline: message_*, tool_execution_* (incl. parentToolCallId), queue_update, compaction_*, auto_retry_*, session_info_changed, thinking_level_changed, extension_ui_request, extension_error, entry_appended (controlroom entries).
  • pi's RPC is unversioned: pin pi, record fixtures/pi-rpc/ per pinned version, and tolerate unknown events.
  • Signals: pi exits on SIGHUP, so never deliver HUP to its group.

6.4 FakeDriver

A deterministic in-process driver for runtime unit tests (no processes). ACP and the prototype's AcpDriver are dropped: controlroom integrates deeply with pi only.

6.5 Stores

  • Agent daemon: agent.sqlite with versioned migrations (user_version) from day one. Tables: sessions, workspaces, shells, agent_sessions, queue, ops (pruned), requests, timeline items (materialized by session/item, with checkpoints), todos, jobs, per-host job cursors and pending follow matches, children, grants cache, settings, and a persisted rev log. Pending host calls are kept in memory and rebuilt from the transcript at restart.
  • Host daemon: host.sqlite: workspaces {id, session_id, path, root, profile}, shells {id = <session>/<name>, workspace_id, supervisor, log, cwd}, jobs, the job event log, and the journal {call_id, session_id, op, args_hash, state: running|done|lost, result, output_ref, acked} (acked rows dropped, others after 24 h).
  • Bind the socket before recovery. Attach supervisors concurrently. Slow work stays off the connection loop.

6.5b Tool executor (host)

  • Exactly once per tool: reads are idempotent; write is journaled, atomic (temp file, fsync, rename) and compare-and-swap; bash is at-most-once (journaled before it reaches the shell; a resend attaches or returns the result, never reruns); jobs are at-most-once by call id. After a daemon restart, a write is resolved by the file's hash and a command by its PTY supervisor's log, else it is lost.
  • Shell integration: the agent's command is written to a file and the shell runs __cr_run <call id>, which echoes it for humans, emits OSC 133 C, sources the file and lets PROMPT_COMMAND emit D;<exit> and OSC 7. The result is the bytes between C and D.
  • Timeouts (default 600 s) are enforced on the host, so they hold while the link is down. Cancel is ETX into the PTY, SIGKILL of the foreground group after 5 s.
  • Waiting for input: the PTY's foreground group sleeping in a tty read for 2 s without output (tcgetpgrp + /proc/<pgrp>/wchan) flags the call.
  • Search embeds ripgrep's crates (ignore, grep-searcher, globset), so hosts need nothing but bash and nono; windowed reads use a per-file line-offset index keyed by (inode, size, mtime).

6.6 Lifecycle (finish what the prototype left undone)

  • Idle-stop (default 48 h): only when resumable, the queue is empty, and there's no live work (jobs, children, asks, pending host calls).
  • Retention: closed sessions are purged after N days. The default is to keep everything forever.
  • Reboot handling: dead supervisor → interrupted or dormant.
  • Resume: via the driver.
  • Start fresh: optionally includes a history export.
  • Boot start (host daemons): linger plus a systemd user unit, else @reboot, else lazy start (reported by doctor). The agent daemon is a system unit on the server.
  • Link loss pauses, it doesn't fail: a tool call on an unreachable host waits up to the machine's grace (default 10 min) and is resent by call id after the reconnect; after the grace it fails with connection_lost and its late result is injected when the host returns. A host-daemon restart (new epoch) reopens dead shells in their last cwd with a reset notice.

8. Agent runtime primitives (agent daemon)

PrimitiveImplementation
InjectionDelivers an item into a session's next turn, with an origin (user, job, child, message, answer, todo, continue, tool_late, workspace). pi uses steer/follow_up. It's the single path for job completion, child results, inbound messages, non-blocking answers, todo edits made by the user, late replies, late tool results and workspace notices (host unreachable past the grace, workspace added or removed).
Job (background task)A supervised process on the host of a workspace (job run {command, machine?, cwd?, timeout?}; supervisor kind job, under that workspace's sandbox, with an optional timeout). Jobs survive pi, agent-daemon and host-daemon restarts and keep running while the link or the server is down. Their output goes to the job's transcript and to a plain-text log file on that machine, which the agent reads with read/grep: <workspace root>/.controlroom/jobs/<job-id>.log, shown as machine:path (stdout and stderr interleaved, append-only; .controlroom/ is git-ignored automatically).
Event log and exactly-once wakes: the host follows each job's output and appends started · progress {lines, offset, matches} · follow · unfollow · killed · exit to a persisted event log (started before the process exists; exit {lost} when its supervisor died with the host). The host never decides wakes. The agent daemon keeps a cursor per host, resubscribes from it after every connection, and commits the new cursor, the pending follow matches and the wakes they produce in one transaction, with deterministic wake ids, so each wake is delivered exactly once (docs/design/remote-tools.md §3.6). While a host is unreachable nothing is invented: running jobs still count as live work and one notice per outage is injected after the grace.
Wakes:
  • Exit wake (always on): when the job exits, the agent is woken with the job id, exit code or signal, duration, total line count and the log path.
  • Following is a separate, optional subscription: job.follow {job_id, buffer_seconds = 15, pattern?, from = "unseen" | "now"} and job.unfollow {job_id}.
    • When followed lines appear (any line, or only lines matching pattern, a regex such as ERROR|FAIL|panicked), the agent daemon waits buffer_seconds (measured from the first match's host timestamp) to batch them. It then wakes the agent with the job id, the number of new or matching lines and their line ranges, and the log path, plus a hint to read it with grep/tail/sed -n 'a,bp'.
    • from: "unseen" (default) covers all output the agent hasn't been told about, so following right after run can't miss lines.
    • Calling follow again updates the settings. Following ends automatically when the job exits, and the exit wake still fires.
    • Wakes from several followed jobs that land in the same buffer window are merged into one wake.
    • The user can also unfollow a job from the UI, to stop noisy wakes. Following stays an agent decision.
  • Logs are never dumped into the context. Wakes carry only metadata and the path, and the agent reads what it needs. Wakes use injection: they start a turn when the agent is idle, or arrive as a steer or follow-up when it's busy.
SubagentA child controlroom session (parent_id) with any model. It has its own transcript, sandbox, shells and requests. A child inherits (a subset of) the parent's workspaces, or a directory or worktree inside one; a child that would get a workspace the parent doesn't have needs approval (a spawn request). Attention rolls up to the parent. await resolves with its result (or connection_lost) by injection.
RequestQuestions are non-blocking only. ask_user returns immediately with a question id and the reminder: "Question sent; the user will answer asynchronously. Keep working on other items. End your turn only if you truly can't make progress; the answer will wake you." The answer (or a Dismiss, which counts as "declined") is injected. The agent can withdraw a question. There's no escalation and no blocking variant.
Approvals stay blocking by nature, because they gate an action already in progress: permission, sandbox (raised by a workspace's sandbox on its host), spawn, contact, privileged and terminal_input (a command waiting for the user to type in its terminal). pi's own native blocking dialogs (extension_ui_request select/confirm/input) are shown as a dialog and answered as usual, but the agent instructions steer agents to use ask_user instead.
Todo listPer-session and shared: both the agent and the user edit it, and every change records who made it. Items: pending · in_progress · done · blocked(reason) · skipped. Can be seeded from a task's checklist.
Auto-continueWhen the agent ends its turn and open todo items remain (pending or in progress), the agent daemon automatically restarts it with a continue run, unless:
  • a question is open (its answer will wake the agent instead);
  • a background task is running (its follow or exit wake will wake the agent instead). Awaited subagents, outstanding message asks and tool calls waiting for an unreachable host count as background work too;
  • an approval is pending, the run failed or was cancelled by the user, or the queue has items (queued prompts go first);
  • auto-continue is off for the session.
It pauses with attention when only blocked items remain, after 3 runs with no progress (stalled), or when the budget runs out. A user cancel pauses it too.
MailboxPer-session outbox and inbox: send, ask (expects a reply), reply. Every session lives in the agent daemon, so delivery is local, under the contact policy (§10). Every operation returns an explicit outcome; connection_lost remains only for host-bound work.

8.1 Schedules (owned by the web server)

  • What they are: a schedule is attached to one session and wakes its agent with a canned message on a configurable schedule. Example: every weekday at 09:00, "Check inbox/ and process anything new".
  • Owned by the controller, not the agent daemon. The web server already knows every session, so schedules live in the controller store: schedules {id, owner, session_id, name, spec: cron | interval, timezone, message, enabled, if_busy, missed, next_run, last_run, last_outcome} (session ids are global). No boot-start requirement on execution hosts.
  • Firing: the controller's scheduler sends session.prompt with deterministic op_id = schedule_id + scheduled_time, so a controller restart or retry can never double-fire.
    • Dormant sessions are resumed lazily by the agent daemon as usual.
    • The run's trigger shows as schedule: <name>.
    • The agent sees it as a normal prompt with origin schedule.
  • If busy (if_busy): queue (default) or skip.
  • If the agent daemon is unreachable at fire time, retry until the next scheduled time, then record missed. An unreachable workspace host doesn't block the prompt; the agent's tool calls there wait.
  • After controller downtime (missed): skip (default) or run_once.
  • Closed sessions disable their schedules.
  • UI: a Schedules panel on the session (add, edit, enable/disable, "run now", next and last run with outcome), a Settings › Schedules overview, and schedule-triggered runs badged in the timeline.
  • Not exposed to agents in the first release; an agent can't schedule itself. Event triggers (file, webhook, git) come later with the same shape.

9. Agent tools and front ends

There are three layers:

  • Tools (only things the agent initiates). These are grouped tools, each taking an action, provided by @controlroom/pi:
    • File and search tools on the hosts: read {path, offset?, limit?}, write {path, content}, edit {path, edits[]}, grep, find, ls replace pi's built-ins under the same names and argument shapes, with paths as machine:path (e.g. devbox:~/src/api/main.rs; ~ is the remote home, relative paths resolve against that machine's workspace root, a bare path is accepted only with a single workspace). pi runs with --no-builtin-tools. Each is served by host.call (agent API); edit runs pi's own edit logic over read_bytes and a compare-and-swap write, so a concurrent change is a conflict, never a lost update;
    • bash {command, shell?, timeout?}: replaces pi's built-in bash. It runs in a persistent, named shell on a workspace's host (default: the machine name, or <machine>-<dir> with several workspaces there), in the session's collaborative terminal ("Terminals"), sandboxed by the workspace's profile. Every result starts with [shell devbox · devbox:~/src/api · exit 0]. shell_new {name, at: machine:path} gives a fresh shell; shell_list;
    • terminal_read {shell?, last_lines | since_mark}: reads the session terminal, including commands the user ran;
    • bash_privileged {command, reason, cwd?}: unsandboxed, and every call needs human approval ("Terminals");
    • ask_user {questions}: always non-blocking; withdraw {question_id};
    • todo {list|add|update|complete|block};
    • job {run {command, at?: machine:path, timeout?} | follow {job_id, buffer_seconds?, pattern?, from?} | unfollow {job_id} | status | kill}. run returns {job_id, log_path}, and the exit wake is always on. There's no logs action: the agent reads the log file;
    • subagent {spawn|await|steer|cancel};
    • message {peers|send|ask|reply, queue_if_offline?};
    • notify_user.
  • Automatic behavior: injection, auto-continue, outcome reporting, and a short controlroom section in the system prompt that explains these mechanics.
  • User-only, never exposed as tools:
    • approving the agent's own requests;
    • widening contact (same-task links, grants);
    • giving a subagent a workspace its parent doesn't have;
    • auto-continue settings or budget;
    • sandbox grants;
    • anything in sessions the agent can't reach.

@controlroom/pi (TypeScript, pinned in the bundle):

  • Registers the tools natively and renders them in pi's TUI (the remote tools reuse pi's own renderers, so $ cmd, edit diffs and read path:range look as usual).
  • Talks to the agent daemon over the session's unix socket, the only socket granted in the sandbox, authenticated with a per-session token from the env-file.
  • Agent daemon → extension: notifications on that socket (state, session.info, host.output), never commands on pi's stdin.
  • System prompt: in before_agent_start (re-read every run) the extension adds the workspaces' instruction files as project context with machine:path names, a <workspaces> section (machines, roots, shells and their cwd) and the workspace skills; pi's own context-file and skill discovery is off.
  • Durable extension state: appendEntry.
  • Telemetry: tagged widget lines.
  • Bridges permission provenance from pi-permission-system (permissions:* events).

9.1 ACP agents (Claude Code, Codex): dropped

Removed from the design: controlroom integrates deeply with pi only. There is no AcpDriver, no controlroomd mcp, no pi-acp and no ACP fixtures. The notes below are historical and must not be built.

  • They keep their own harness. Their built-in tools (edit, bash, search, web, their own Task subagents and background shells, TodoWrite) stay as they are. controlroom adds its tools as an MCP server. It does not replace their tools.

  • What maps from native ACP:

10. Contact policy

  • Default deny. Agents can only list sessions they're allowed to reach.
  • Same task: sessions linked to the same kanban task can see and message each other, wherever their workspaces are. Linking a session is the user's affirmative act.
  • Parent and child: they can always talk to each other.
  • Anything else raises a contact request to the user (allow once / allow this pair / deny). It behaves like a permission (attention and push). Grants are stored by the controller and can be revoked.
  • Spawning with new reach: a child that would get a workspace its parent doesn't have always needs approval, raised as a spawn request with Allow or Deny. Children within the parent's workspaces follow a per-session or per-project setting (default: allowed).
  • Who sees a contact request: it sits on the requesting session, which waits for the answer. The target session sees nothing until it's granted; then both timelines show a grant notice. Task detail lists pending contact requests among its sessions.
  • Delivery is local to the agent daemon, which holds every session; the controller supplies the policy inputs it owns (task links, grants). Messaging fails closed and always reports the outcome. A peer can't be unreachable, but an ask can still expire; in-flight asks and awaits resolve instead of hanging. Late replies are injected and marked late.
  • Message contents are visible in both sessions' timelines.

11. Sandboxing (nono 0.80.0)

Spike result: GO. pi 1.2.0 with its extensions ran under nono on aarch64 NixOS (kernel 6.18, Landlock V6):
  • bash, children, detached grandchildren and pi's own file tools were confined to the working directory;
  • both provider types worked with no real credentials in the sandbox;
  • only allowlisted hosts were reachable, with direct TCP, UDP and DNS-over-nscd blocked;
  • webhook approvals worked;
  • stdout carried only JSONL;
  • exit codes passed through, and it ran detached;
  • overhead was about 50 ms at launch and about 0.25 s added to pi's startup.

There are two sandboxes, both generated nono profiles:

  • Server, per session (pi): an empty scratch workdir, read-only /nix/store and the bundle, the session's agent/home/tmp, the session's agent socket as the only unix socket, and only the model routes on the network (credentials injected by cmd://). No project files, no SSH keys, no route to hosts. --no-builtin-tools means pi can't start shells. The spike ran pi 1.2.0 exactly like this.
  • Host, per workspace: the workspace root read-write plus the level's reads, the session's domains, mediated commands and job secrets (injected by the host's nono proxy). Everything the agent triggers on that host runs inside it: PTY shells, jobs, and the per-workspace fs worker (controlroomd workspace-exec) that serves the file and search tools, so the unsandboxed host daemon never touches project files on the agent's behalf. Two sessions on one path get two profiles, each with its own grants.

Model credentials never leave the server; host secrets never reach the server's sandbox.

11.3 Credentials

  • API-key providers: cmd:// → controlroom-agentd credential, which prints the key from the agent daemon's credentials (LoadCredential/sops), outside the sandbox.
  • OAuth subscriptions: a one-time controlroom-agentd login <provider> on the server (a UI flow later). The sandbox auth.json holds a synthetic unsigned JWT that carries only the non-secret claims pi needs (e.g. the account id), with a far-future expiry. The agent daemon is the only process that refreshes the token, using pi-ai's locked refresh against its real auth.json. A refresh attempted inside the sandbox fails closed.
  • Residual risk: sandboxed processes can use the injected credential on allowed hosts, so endpoint policies are mandatory. Never put secrets in argv, because /proc/*/cmdline is readable.

11.4 Approvals

  • Approvals come from the host sandboxes. The webhook URL is http://127.0.0.1:<port>/nono/v1/<workspace>/<secret> on the host. Correlate on the URL, because endpoint requests carry no session id. The sandbox can't reach loopback TCP.
  • The path: nono → host webhook → host daemon approval.request → controller (hostops.notify) → agent daemon, which raises request{kind: sandbox, blocking: true} on the workspace's session (attention, push) → user → agent daemon → controller → host approval.respond → nono. Requests map to:
    • command → "run …?"
    • capability → "read/write path?"
    • endpoint → "call METHOD path?"
  • The reply is {"decision":"granted"|"denied","reason"}. A timeout means deny. Use a long timeout_secs for human waits, or deny fast and let the agent retry after the user grants.
  • Grants: a path granted at runtime is remembered for the nono session. Standing grants (paths, domains, commands) are profile changes: the workspace's profile is rewritten (workspace.open again) and shells and jobs started afterwards use it. Domains can't be approved at runtime in 0.80.

11.5 Hard rules and risks

  • Never use nono registry packs, nono pull or ns/name profiles. Pack wiring mutates the agent's config: it appended to a home-manager-managed settings.json, and there's no flag to disable this in 0.80.
  • Run nono with controlroom-owned XDG_STATE_HOME/XDG_CONFIG_HOME, plus NONO_NO_UPDATE_CHECK=1 and a dead NONO_REGISTRY.
  • Pin 0.80.0 (from nixpkgs or the upstream flake) and re-run the spike's checks on every bump.
  • Without capability elevation, denials don't show up in diagnostics. Use the audit trail and nono why.
  • Command mediation on NixOS is fragile: it needs exact store-path pins and only allows PATH binaries to run. Keep the mediated set small and test each command.
  • Clean up leaked /tmp/nono-* directories.
  • Known limitation (accepted): command mediation is a policy layer, not a security boundary. nono 0.80 grants execute on every directory the session can write (including the working directory), and mediated commands are identified by file identity. An agent can therefore copy git and its helpers into its cwd and push without the approval card. What still bounds it: writes stay confined (Landlock), only allowlisted hosts are reachable, and only the credentials the session holds work. Treat the git push approval as a policy aid. Possible fix (not scheduled): give git-host domains and git credentials only to the mediated git/gh command sandboxes (command-scoped domains and credentials in sandbox profiles, a protocol change), deny proxy CONNECT to port 22 for the session, and keep SSH keys out of the session HOME (a nono agent-socket credential for git→ssh).

Per-session sandbox levels (one level for the session; it shapes every workspace's host profile, while pi's server profile stays fixed):

  • strict (the default): the workspace root and the session's own dirs only;
  • relaxed: adds read-only home config such as git;
  • off: shown with a warning badge (shells, jobs and file tools on the hosts run unsandboxed).

doctor (of the agent daemon and of each host) reports the Landlock ABI and whether nono is available.

12. Controller and web server

  • Port the prototype's client store (owner-scoped repos, sealed keys, dangling task links allowed), keys and rotation, machine manager, attention, push and dedup, OIDC, hardening and static serving. Fix the review findings on the way in.
  • Hub: split it into modules and add an event bus (connectivity, summary changes). Sessions come from the agent daemon (global), machines from the host connections. Policy, project membership, workspace overlaps and the timeline cache subscribe to the bus instead of growing a monolithic state.
  • Host router: carries the agent daemon's host requests (hostops.*, protocol §5): sends each pending request to its connected host, resends unanswered ones after a reconnect (every host method is idempotent), forwards every host notification, and reports machines (names, availability, epochs, grace).   • Agent daemon client: one local socket connection; resubscribes (sessions.subscribe, hostops.subscribe, open sessions) after a reconnect; the scheduler fires session.prompt on it.
  • RPC: split by namespace and make pass-through methods table-driven. Cap concurrency per WebSocket connection, define the ordering contract, and close sockets on logout or expiry.
  • Store writes touch only the columns that changed. Whole-row read-modify-write across an await caused the prototype's lost-update bug.
  • Auth: sessions are tagged with the auth mode and subject, and the allow-list is re-checked on every request.
  • Host client: per-call timeouts (except tool.run, which lasts as long as the command), cancellable post-connect steps, the controller id in hello (single-controller rule), and the host's epoch.
  • Bootstrap: run the new binary and check --version before swapping current. Keep the previous target for rollback if hello fails. Confirm the old daemon actually stopped. Pin the host-key algorithm.

18. Process rules (for the supervising agent)

  • Worktrees: one git worktree per workstream under a sibling controlroom-worktrees/ dir. Workers commit only to their own branch. The supervisor rebases and merges. Create the worktree, check it exists, then launch the worker (launches can race with directory creation).
  • Gate every merge on nix flake check, and check the real exit status (never pipe through tail without pipefail). Nix only sees tracked files, so git add first. Regenerate Cargo.lock on conflicts.
  • Never git commit -a. Stage files by name. README.md is human-only: never edit or commit it. Planning files are uncommitted.
  • Contract changes: the protocol crate owns the TS. Generated files are read-only for the UI. Every contract change is announced to the UI owner. Minimal mechanical mock or fixture edits are allowed and must be listed.
  • Version bump on every daemon change, because auto-upgrade detects changes by version.
  • Tests: offline and deterministic (gate steps, not sleeps). Integration tests kill every process they spawn, even on failure.
  • Never use nix profile add/install, and never touch the user's ~/.pi/agent, home-manager files or ~/.ssh during experiments. Run nono with isolated HOME and XDG dirs.
  • Privacy: no real hostnames, usernames, domains, provider URLs, model ids or secrets in code, docs, fixtures (sanitize them) or commit messages. American spelling.
  • Test servers: keep a GC root (nix build -o …) for any binary you run, and start servers only after the build finishes.

22.1 Agent shells (persistent state)

  • State persists within a shell: cd, exported env vars (e.g. KUBECONFIG), functions and venv activation carry over between the agent's bash calls and the user's commands in the same shell. This stops agents from repeating env assignments in every command.
  • Fresh state on request: shell_new {name, at: machine:path} opens a new shell (a new tab) with a clean login environment in a workspace (default the root). Each workspace starts with one shell named after its machine (<machine>-<dir> when the session has several workspaces there). If a command runs exit, or the host restarts without the shell's supervisor, the shell is reopened in its last directory and the next result says its variables were lost. bash {shell} targets a named shell. Separate shells also let independent commands run in parallel.
  • Every tool result starts with a context header [shell devbox · devbox:~/repo/sub · exit 0] (cwd from OSC 7), so state drift is always visible to the agent.
  • Command boundaries: the host daemon wraps each agent command with OSC 133 shell-integration markers (prompt, command start and end with exit code), so the tool result gets exactly that command's output (ANSI-stripped, length-capped, with a pointer to the full output on the host).
  • Serialization: one command at a time per shell. If the user is mid-typing at the prompt, the agent's command waits, and the pane shows "agent wants to run: …" with [Let it run].
  • Avoiding needless prompts: agent shells set PAGER=cat GIT_PAGER=cat MANPAGER=cat, GIT_TERMINAL_PROMPT=0 and DEBIAN_FRONTEND=noninteractive.
  • Waiting for input: when a command is waiting on terminal input (a password, a confirmation, a pager), the tool call is marked "waiting for input in terminal". It becomes a blocking attention item with push, and the user types into xterm. Passwords are not echoed, so they never reach the agent. A timeout applies, and the agent can't type into the terminal itself.
  • Reading the terminal: terminal_read lets the agent read what the user ran ("look at the error I just got"), limited to its own session's shells.
  • Caution: secrets the user exports in the collaborative shell are visible to the agent. Secrets belong in the private terminal.
  • Default shell: the user's login shell (bash or zsh) with the integration snippet sourced. Shells without OSC 133 support fall back to marker echoes.

22.2 bash_privileged

  • Why it exists: nono sets NoNewPrivs, so sudo and setuid can't work inside the sandbox. bash_privileged {command, reason, cwd?} is the only way out.
  • Every call needs approval. There's no auto-run, no "always allow", no patterns and no session grants.
  • The approval card shows the exact command, the reason, cwd and machine, with Approve / Edit & approve / Deny (reason). The approval is bound to the exact command text. If the command was edited, the agent is told what actually ran. A denial's reason becomes the tool result.
  • Where it runs: unsandboxed as the user, in the privileged pane, using the user's login environment (no injected proxy credentials or session tokens). It's interactive, so sudo or ssh prompt the user. Output and exit code go back to the agent (ANSI-stripped and capped). Approval itself never times out; it waits for the user. Once the command is running, a wait for terminal input (e.g. the sudo password) times out after a configurable 10 minutes, and the agent gets "timed out waiting for user input".
  • The card warns about anything that would outlive the call (&, nohup, setsid, disown, systemd-run, …), because those processes run unsandboxed.
  • Audit: a distinct timeline item records who approved it (device label), the command that ran, and the exit code. Subagents follow the same rule, and their requests roll up to the parent.

22.3 Jobs on PTYs

  • The terminal shows raw output (colors, progress bars), and the user can type into it, e.g. to answer a prompt.
  • The agent's log file <workspace root>/.controlroom/jobs/<id>.log (on the job's machine) is an ANSI-stripped plain-text copy (carriage-return progress lines collapsed). Follow and exit wakes work as described in "Job".

22.4 Private terminals

  • Scope: opened from a project on a machine and directory the user picks. Listed under the project and persistent until closed.
  • Visual identity: a distinct background tint and frame (e.g. a deep violet or charcoal theme in xterm), a lock icon, a "PRIVATE · agents can't see this" badge on the pane and tab, and its own section in the terminal list.
  • Isolation:
    • not listable or readable through any agent tool or API reachable from a sandbox;
    • the supervisor state lives outside every session directory (mode 0700);
    • no disk log;
    • excluded from previews, push, the away summary and search.
